# Observability shift runbook

The fictional Cedar monitoring system supports a small volunteer operations rota. It collects request metrics, structured application logs, and selected request traces. Each signal answers a different question. A monitoring dashboard is a starting point for investigation, not an instruction to restart everything that appears red. Before acting, record the affected service, approximate start time, and a user-visible symptom that can be checked again after recovery.

## Metrics and aggregate trends

Metrics describe aggregate behaviour such as request rate, error ratio, and latency distributions. The workshop compares the current interval with a recent quiet interval before drawing conclusions. A high request count can explain increased load without identifying which individual request failed. Check units and aggregation windows when two panels appear inconsistent; a five-minute rate and a total counter do not express the same quantity.

The latency dashboard includes a percentile view alongside request volume. A quiet service can produce unstable percentile estimates from very few observations. Operators therefore record the number of requests in the selected interval when discussing a latency spike. The dashboard cannot by itself prove that a particular database statement caused the spike; that requires more specific evidence from logs or traces.

## Logs and request identifiers

Use the request identifier to find related application log entries for one failed request. Structured fields are preferable to guessing from nearby timestamps when several requests run at once. The workshop records the route, outcome, and request identifier without storing passwords or recovery tokens in logs. An absence of matching log entries can mean the request never reached the application, but first verify the selected service and time range.

A log entry is an event, not a complete description of the entire request path. When the browser reports failure but the application log shows success, inspect the gateway and client-facing stage as well. Preserve the original identifier in the incident ticket so the next operator does not search for a different request generated by a later refresh.

## Traces across components

A distributed trace links timed spans across participating components. Use a trace to investigate where time was spent along a request path. The workshop includes gateway, application, and database-call spans when instrumentation is available. Missing spans do not establish that a component was fast; the component may simply be uninstrumented or excluded by sampling. Read the sampling and propagation assumptions before interpreting an incomplete trace.

Compare span durations with the overall request duration and look for gaps as well as slow spans. Parallel spans can overlap, so adding every span duration is not a reliable calculation of elapsed request time. A trace is particularly useful after metrics identify a sustained latency change, but one unusual trace should not be presented as the performance of every request.

## Alert acknowledgement and resolution

Acknowledging an alert records that someone is investigating it. Resolving an incident requires evidence that the user-visible symptom has recovered. The workshop's acknowledgement action does not silence all future alerts or change the service configuration. If an alert keeps firing, update the investigation record rather than repeatedly acknowledging it as a substitute for understanding the ongoing condition.

The closing procedure deliberately spans two operational steps. First, repeat the same external check that demonstrated the original symptom and record its result.

Then watch the error ratio remain below the workshop's alert boundary for ten consecutive minutes before marking the incident resolved. These two requirements belong together: a single successful request and a sustained aggregate recovery provide different evidence. Do not close the incident based only on the acknowledgement timestamp.

## Shift handover checklist

- Include the service, time range, and original symptom.
- Link relevant metric views and request identifiers.
- Distinguish observations from suspected causes.
- State which recovery checks remain incomplete.

An incomplete investigation is acceptable at shift change when the evidence is preserved. An undocumented restart is harder to learn from because it can remove the state that explained the failure.
